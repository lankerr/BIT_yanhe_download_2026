# 延河课堂限流/风控调研笔记与对策

> 2026-09 整理。全部结论来自**本项目的实测记录与自身日志**（`docs/speed_experiment.md`、
> `utils.probe_yanhe_reachable` 注释、历史 issue），未对延河服务器做任何主动探测或压测。

## 一、已观察到的风控行为（我们的数据）

| 信号 | 观察来源 | 含义 |
|------|---------|------|
| `code=61101114` / "系统繁忙" | probe 实测注释 | cbiz API 域 WAF 拒绝，常包在 **HTTP 200** 里 |
| `/v1/auth/me` 长期静默拒绝 | probe 注释 | WAF 按"接口+客户端特征"拒绝，与 token 无关 |
| "token 风控（之前发生过）" | speed_experiment.md §6.3 | 账号维度存在风控，不只是 IP 维度 |
| "Python 直发 → IP 段识别为工具 → 限速" | speed_experiment.md §5.2c | 疑似按客户端特征/IP 段区别对待 |
| 分片 403 / 卡尾部 | v1.x 历史 | CDN 过载或拒绝时的表现 |
| 签名路径 `_100`→`_200` 变更导致 403 | TEST_REPORT_2026 | 签名机制会随网站前端更新而变化 |

## 二、旧客户端的三个雷点（本项目 2026-09 排查）

1. **被限时 16 线程无感知硬敲**：CDN 一旦开始拒绝，分片线程只把失败丢进补下队列，
   其余线程照常全速请求——这正是让封禁升级的最差行为。
2. **API 重试无退避协调**：m3u8 获取失败 1-2s 间隔连敲 5 次，WAF 激活期间等于火上浇油。
3. **`Xclient-Timestamp` 请求头陈旧**：只在 import 时设置一次，GUI 挂几小时后头里还是
   启动时刻，与查询参数里的新鲜时间戳自相矛盾（已修：`getSignature()` 同步刷新）。

## 三、现行对策（"不触发"而非"绕过"）

原则：**被限就全体退避，成功即恢复**。不做 IP 轮换/指纹伪造/验证码绕过——
token 绑定学生身份，对抗性流量的代价是账号而不是 IP。

| 机制 | 位置 | 行为 |
|------|------|------|
| 全局熔断器 `WafBreaker` | `utils.py`（cbiz/cdn 各一实例） | 任何线程看到 403/429/503 或 `61101114` → 全局冷却 10s 起、连续触发指数翻倍至 60s 封顶；成功一次级别归零 |
| API 全局限速 | `utils.direct_get` → `_pace_api()` | cbiz 请求全局串行，最小间隔 0.8s |
| 熔断只认"服务器拒绝" | — | 弱网超时/断连**不**触发熔断（避免重演 AIMD 死亡螺旋，保住 v3 引擎的弱网吞吐） |
| 自动接线 | `utils.direct_get` | 分片/m3u8/key/音频所有调用点自动获得上述行为，无需各自判定 |

## 四、本地压测验证（`scripts/waf_breaker_check.py`）

用本地 mock 模拟延河 WAF（窗口阈值 + 惩罚期，HTTP 200 包 `61101114`；CDN 回 403），
**零真实请求**打延河。11/11 通过，关键结果：

```
16 线程被限 3 秒期间：
  旧客户端（无熔断）: 仍发出 ~4600 个请求
  新客户端（熔断退避）: 仅发出 ~26 个请求   （↓约 180 倍）
```

复跑：`python scripts/waf_breaker_check.py`

## 五、如果将来又被限（排查顺序）

1. 看 `download.log` 里有没有 `[限流熔断]` 行——有，说明对策在正常工作，等冷却即可；
2. 熔断频繁触发（几分钟一次）→ 说明当前网络/账号特征已被重点关照：
   换时段、降低 GUI 并发到 8、或间隔下载多个章节，别连轴转；
3. 出现 403 且提示 Token 过期 → 重新取 Token（那是签名/token 问题，不是限流）；
4. 签名整体失效（m3u8 全 403）→ 网站前端更新了签名算法，需要对照
   `utils.py` 里的 magic/`_200` 标记与最新 main.js。
