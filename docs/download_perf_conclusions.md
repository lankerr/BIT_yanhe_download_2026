# 下载速度优化结论：瓶颈定位与"要不要重写"的最终答案

> 2026-09-05 实测。数据来源：真实 CDN 压测（K 扫描 × 2 轮交错）+ localhost 无限速对照实验。

## 一、瓶颈定位（三层对照）

| 层 | 实测吞吐 | 结论 |
|----|---------|------|
| 真实延河 CDN（内网 10.0.34.x，K=32） | **9.26 MB/s 持续 / 19.31 MB/s 5s 峰值** | 当前瓶颈：**服务端/接入网** |
| 客户端自身（localhost 无限速，完整引擎） | **355-535 MB/s**（K=8/16/32） | 客户端利用率仅 **~2.6%**，余量 38-58 倍 |
| 并发扫描 | K=16-32 饱和区 8.15-9.26；K=48/64 降至 5.5-6.6 且自扰重试 | 甜蜜点已找到，堆并发无益 |

## 二、"汇编/C/Rust 重写 m3u8dl"的答案：无收益，不做

字节搬运实际发生在：内核 socket 缓冲 → OpenSSL/urllib3（C）→ 磁盘（内核）。
Python 层只剩 1MB 粒度的分块循环（已优化）。客户端在 355+ MB/s 区间运行而
网络只给 9.26 MB/s——把一个利用率 2.6% 的组件重写为汇编，速度不会有任何
变化。同样的否决理由适用于 asyncio 重写（socket 相同）。

## 三、还能不能更快？真实杠杆清单

1. **时段**：5s 峰值能到 19.31 MB/s 说明服务端允许突发、持续段被整形——
   网络空闲时段（清晨）持续值有望上移，压测报告可分时段复测验证。
2. **接入介质**：换有线/换接入点（WiFi 空口竞争是常见隐形上限）。
3. **多课程并行**：若整形按"单课程连接"实施，两门课同时下可能各得 9 MB/s
   ——但这属于加压行为，仅限校内自用场景谨慎使用。
4. 服务端整形策略（每 IP / 每连接 / 每时段）不由客户端决定，到此为止。

## 四、给用户的建议档位

- GUI 默认 K=16（8.15 MB/s，p95 段耗 11.1s，零重试——最稳）
- 追求极速 K=32（9.26 MB/s，+13.6%，p95 段耗 19.4s，零重试）
- 不要用 K≥48（更慢且产生自扰重试）
